# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

ParaBear is a macOS menu-bar utility (SwiftUI + AppKit, Swift 6.2, macOS 15+ target) — a bear-under-a-parachute widget that flies in from the top of the screen to announce upcoming Calendar events, then drifts down and away. It's a Swift Package executable, not an Xcode project.

## Commands

```bash
swift build              # build
swift run ParaBear        # run the menu-bar app
swift test                 # run all tests
swift test --filter WindSwayMotionTests           # run one test target/suite
swift test --filter WindSwayMotionTests/travellingLeansTheBearTheOtherWay  # run a single test
```

Tests use the `Testing` framework (`@Test`, `#expect`), not XCTest — see `Tests/ParaBearTests/`.

Packaging into a real `.app` bundle (release build, Info.plist, entitlements, ad-hoc codesign) is done via:

```bash
Scripts/package_app.sh
```

That script does one thing beyond the obvious: it copies SwiftPM's generated resource bundle into `Contents/Resources`. Without it the packaged app has no artwork at all — see **Resource loading** below.

Calendar access (EventKit) only works when running as a bundled `.app` with `NSCalendarsFullAccessUsageDescription` present — `swift run` during development will not be able to prompt for/receive Calendar authorization the way the packaged app does.

## Architecture

```text
Sources/ParaBear
├─ App        — ParaBearApp (SwiftUI @main + Settings scene), AppDelegate (wires everything together), MenuBarController
├─ Domain     — small pure value types/enums: CalendarEvent, BearMood, ReminderMilestone, PlannedFlightSpeed, WindStyle, RigPose
├─ Services   — CalendarService: EventKit integration, authorization, polling; PackagedResources: where the art actually is
├─ Overlay    — BearOverlayWindowController: the borderless NSPanel and its per-frame drift/sway physics; RigHostingView
├─ Features   — SwiftUI views + view models for visible product behavior
├─ Animation  — reusable motion math (FloatingMotion)
├─ Settings   — SettingsStore (UserDefaults-backed @Published prefs) + SettingsView
└─ Assets     — SVG source art (Bear/, parachute.svg) bundled as package resources
```

Each folder owns one reason to change. When adding code, put pure math/models in `Domain` or `Animation` (so they're unit-testable without AppKit), UI in `Features`, and system integration in `Services`.

### Control flow

`AppDelegate.applicationDidFinishLaunching` is the composition root: it builds a `CalendarService`, an `EventTimelineViewModel` (the `@MainActor` view model driving countdown/mood/reminder state), a `BearOverlayWindowController` (owns the actual floating `NSPanel`), and a `MenuBarController`. There's no DI container — dependencies are just passed through initializers.

- `CalendarService` polls EventKit every 60s (`EventTimelineViewModel.start()`), reads only events in the next hour, and publishes `todayEvents`/`authorizationState` via Combine. It deliberately does **not** decide which event is the current one: that rule needs state the service does not have, and deciding it here would leave the 60s poll racing the 5s tick for the last milestone — a poll that retired an event a second before the tick that was going to fire for it would swallow the flight.
- `EventTimelineViewModel` ticks every 5s to pick the current event, recompute the countdown/mood, and check `ReminderMilestone.dueMilestone(for:)`. It tracks `firedReminderKeys` (occurrence + milestone) so a milestone never fires twice, and calling `milestonesHandled(by:)` marks all *earlier* milestones as fired too (so a late-triggered "starting" reminder doesn't also fire the 10/5/3-minute ones).
- An event's life ends at `ReminderMilestone.underway` — one last flight `underwayDelay` (5 min) after it started, and then the event is dropped into `finishedEventKeys` and never chosen again. Something has to retire an event, and its **end time is the wrong thing to use**: a meeting that ran long, or one nobody left, would stand in front of everything behind it for as long as the calendar says it lasts, and back-to-back events would get no warning at all — the one behind it only became `nextEvent` after it ended, by which time its own start was already past and all it could fire was a late "starting". Five minutes in, whoever was going has gone. The drop happens in the same pass (`fireReminderIfNeeded`) and **before** the flight goes out, so the event behind it starts counting down immediately and the flight shows it from its first frame — the card reads the view model live, so retiring afterwards would have the flight display the event it just retired and then switch under itself. Which makes that last flight a *handover*: **that one is done, here is the next**. With nothing behind it there is nothing to hand over to, so `isWorthFlying(_:handingOverTo:)` cancels it rather than parachuting the bear in to report that there is nothing to report. Only the last milestone can be cancelled this way; the other four always have their own event to announce. `nextEvent(from:finished:now:)` and `eventKey(for:)` are stated as pure functions of their inputs because the interesting case — an in-progress event standing in front of the ones behind it — takes half an hour to reach in real time. The key names the *occurrence*, not the series: a repeating event carries one id for every one of its starts, and finishing with this morning's stand-up must not silence tomorrow's.
- Firing a reminder sends a `ReminderMilestone` through `reminderFlights` (a Combine `PassthroughSubject`), which `AppDelegate` observes to trigger `overlayWindowController.playReminderFlight(duration:)`. That call does not necessarily fly: `Domain/FlightQueue.swift` holds it back if one is already in the air. Reminders arrive in bursts — two events back to back put three or four milestones inside ten minutes — and every one of them used to restart the flight where it stood, so a bear halfway down the screen vanished and reappeared at the top; because the restart also reset the drift state, one arriving mid-drag pulled the rig out of the hand holding it. **At most one flight waits**, and the last request wins. A queue would be wrong: the flight carries no message of its own — the card reads the view model live and always shows the current event and countdown whenever it is drawn — so three queued flights are three identical flights in a row. A flight only ends when it leaves the bottom of the screen (`finishFlight`), which is also why a rig being carried holds the queue: `advanceDrift` leaves the descent alone while `isBeingCarried`, so nothing waiting can arrive to snatch it. `hide()` is the other exit and it *drops* what was waiting rather than saving it — a reminder that turns up after the bear was switched off is worse than one that never comes.
- The pointer can pick the whole rig up and put it down anywhere on screen. `BearOverlayView`'s drag gesture reports `NSEvent.mouseLocation` through `BearDriftState.carry(toScreenPoint:)`, which calls the controller back synchronously — the window must move on the pointer's own event, not on the next drift tick. Two traps live here: the gesture's own `translation` is measured in the view's space and the view moves with the window, so following it cancels itself out; and `advanceDrift` must leave the window alone entirely while `isBeingCarried`. While carried, the swing switches from `BearSwing` to `Animation/CarriedSwing.swift`, a damped pendulum integrated on the drift timer — the rule-based swing reads the motion happening *now*, and a hand holding still emits no events, so it would freeze mid-tilt. The hand's speed is sampled from `NSEvent.mouseLocation` on the timer's steady clock rather than from the gesture, for the same reason. On `drop()` the controller calls `configureBroadSwayFromCurrentPosition` so the drop point becomes the new centre of the sway and the descent carries on from there. Horizontal placement is bounded by `centerTravelBounds`, which keeps the card 24pt clear of either screen edge.
- The panel is 500pt wide so the rig can hang off a screen edge, but the rig is 244 at the canopy and 106 at the bear — **most of the window is empty air over somebody's desktop**, and it used to swallow every click that landed there. `Features/RigLayout.swift` states where each part sits inside the window, once, because two things need it: `BearOverlayView` stacks the parts from it, and the window needs the opposite — where the rig is *not*. Two things it is worth knowing were tried and do not work. `contentShape` cannot do it: SwiftUI hit testing chooses which *view* receives an event the window already owns, and `NSHostingView` answers `hitTest` with itself for every point in its bounds even where the content is `Color.clear`; the `.contentShape(Rectangle())` that used to sit on the rig's 500pt frame is what handed the padding to the drag gesture in the first place, and it is deliberately gone. Overriding `hitTest` on the hosting view does not do it either — refusing the event means *nothing* takes the click, not that the application underneath gets it, which is the whole content of `Overlay/RigHostingView.swift`. The only switch that makes a window transparent to the pointer is `NSWindow.ignoresMouseEvents`, so `updateClickThrough` steers it from the drift loop — which already runs every frame the rig is on screen — reading the pointer from `NSEvent.mouseLocation`, because a window that is ignoring mouse events receives none to track with. It is forced off while `isBeingCarried`: the hand can outrun the rig, and a window that stopped taking events mid-drag would drop the bear wherever the pointer left it. `passesThrough(pointer:windowFrame:pose:)` is stated separately because the screen-to-rig conversion — screen coordinates run up from the bottom, the layout is stated down from the top — is the one thing in it that can be silently wrong.
- The region is the rig's **current outline**, not a box, and that is what `Domain/RigPose.swift` is for: `BearOverlayView` writes the frame's drift and bear angle back into `BearDriftState.rigPose` as it draws — the view is the only thing that knows, the window the only thing that can act on it. A box big enough to hold every angle the bear might be leaning at is 291pt wide for a bear that is 106, because it rotates about the top of its head and its feet reach 78pt either side; all of that sat over the desktop taking clicks. So the canopy contributes its drawn dome outline (the corners either side are sky), the lines contribute the fan they actually gather into, and the bear contributes its own box rotated about its head. The pieces are tested one at a time and never concatenated into a single `Path`: under the non-zero winding rule two overlapping subpaths wound opposite ways cancel, and the body box against the canopy hem punched a hole through the region exactly where the two meet. The margins are sized for the rig's *normal* motion — `.windy` at intensity 1 — not for `.stormy` at 1.6, which would take the region to 442 of the window's 500 points and give back most of what this exists to fix; the cost is that the very end of a hard swing can briefly be outside it. `OverlayHitTestingTests` renders the rig and checks every solidly-drawn pixel falls inside the region, which is the only way this stays true as the artwork moves.
- `BearOverlayWindowController` owns a 60fps `Timer`-driven drift loop (`advanceDrift`): vertical descent at constant speed (from `PlannedFlightSpeed.flightDuration` and screen height) plus a horizontal sweep. The sweep is `Animation/DescentSway.swift` — a written-out curve, not a spring, so its speed and turnaround are exact and `placeFlight` can size it to fit the corridor and never clamp it. It replaced a pair of spring integrators whose clamped state kept reporting motion it was no longer making; that is worth not reintroducing. The sweep is multiplied by an exponential settling envelope (`settleShare`) so the flight has an arc rather than being a uniform zigzag; its derivatives are carried through by the product rule, and `nominalSpeed(at:)`/`nominalTurn(at:)` follow the envelope too — otherwise the lean's size depends on where the flight's random phase puts its first peak. Both are read at `Animation/FlightClock.swift`'s time rather than at wall-clock elapsed, and that distinction is load-bearing: the drift `Timer` is in the default run-loop mode, so opening the menu bar's menu puts the run loop into event-tracking mode and the loop stops dead. Wall-clock would then hand the sweep every second the menu was open the moment it closed, reading the curve at a time nothing was ever drawn at and jumping the rig sideways. `FlightClock` only counts frames that happened, capped at `maxStep` each, so the flight sets off again from where it stopped. It also takes — but does not spend — the frames where the rig is in a hand, for the same reason in miniature: banked time would only move the jump to the moment the bear was let go. The window hides itself once it drifts fully below the visible screen.
- The bear's swing under the canopy is **not** simulated. `Animation/BearSwing.swift` states two rules and reads them straight off the rig's current motion: travelling leans the bear the opposite way by `trailDegrees`, and the turnaround at each end of a stroke throws it onward by `turnDegrees`. `Animation/FloatingMotion.swift` (`RigSway`) writes the in-place drift out as a curve rather than integrating it, so its speed and turnaround are exact and the swing can never lag what is drawn. The bear has one lean, so the rules are applied **once**, to the sum of everything moving it: the controller publishes the sweep as a `BearSwing.Travel` on `BearDriftState.descentTravel`, and `WindSwayMotion.sample(alongside:)` adds the in-window drift before calling `BearSwing.degrees(for:)`. Running the rules separately on each path and adding the angles doubles the result — it had the bear reaching 48 degrees during a descent. The descent applies the same two rules to `DescentSway`, read at the same instant as the position — identically to the in-place drift, and `BearSwingTrajectoryTests` measures both paths to keep it that way. `trailDegrees` must stay the larger of the two constants: their ratio decides where the lean peaks, a peak is a stationary point, and a turn-dominant weighting parks that stationary point on the turnaround — leaving the lean motionless at the exact instant the rig changes direction. The invariant both callers must keep: the `nominalSpeed`/`nominalTurn` handed to `BearSwing` come from the very curve being read, so the inputs stay inside the range its response is honest over. Sizing the lean against anything else — a fixed reference, or a spring whose peak has to be guessed — pushes the terms past nominal, where the response flattens, and the lean stops answering the motion at all. Both are pure functions of elapsed time with no state, which is what makes them the best-tested part of the codebase.

### Resource loading

`Bundle.module` is **not** used to find the art, and `Services/PackagedResources.swift` says why. SwiftPM's generated `Bundle.module` looks in exactly one runtime location — `Bundle.main.bundleURL/ParaBear_ParaBear.bundle` — which for a command-line build is the directory beside the executable and works, and for an `.app` is the **bundle root**, where a loose bundle is what `codesign` calls "unsealed contents present in the bundle root": the signature stops verifying. Its only other candidate is an absolute path into the `.build` directory of whichever machine compiled it, which is the trap — the packaged app runs perfectly for whoever built it and traps with "could not load resource bundle" for everyone else. So `Scripts/package_app.sh` installs the bundle in `Contents/Resources`, where a bundle belongs, and `Bundle.packagedResources` looks there first with `.module` as the fallback, which is what keeps `swift run` and `swift test` working — neither has a `Contents/Resources`. The bundle's name is stated in both the script and the lookup and they have to agree; `PackagedResourcesTests` reads the script and checks that, since this is the one packaging mistake that cannot be caught by running the app here.

### SVG assets

The parachute canopy is **not** one of them. `parachute.svg` draws it as a single flat white fill with a raster shadow baked underneath, which is why it read as a sticker; `Features/ParachuteCanopy.swift` redraws that same outline as a `Shape` — the same thing `RiggingLines` does for the suspension lines, using the artwork's own coordinates so both can be checked against the file — split into the parts a light can be aimed at: one `panel(_:in:)` per gore of fabric and one `seam(_:in:)` per fold. `ParachuteCanopyView` then lights it as a **solid dome of fabric**, to the look of an Apple product icon: matte, soft everywhere, all of the depth coming from one light rolling off a curved surface, and no hard lines anywhere. It was liquid glass before — near-clear in the middle with a thick rim, aberration fringes and a rim light — but that reads as glass, and a parachute is cloth. Three layers carry the fabric and all answer to the same light: `fabric` (a slate crown falling to near-black at the hem — the crown never gets near white, or it competes with the text on it), `gores` (the per-panel tones, drawn from the shape's hard vector edges and then **blurred** across the joins by `goreSoftness` — a dome has no facets, and this is the single knob deciding whether the canopy reads as a dome or as a folded paper fan), and `hemShade` (the fabric tucking under at each scallop). Every colour it uses comes from `Features/CanopyPalette.swift`, which states the two schemes side by side. `ParachuteCanopyView` owns *how* the dome is lit and the palette owns *what colour* each layer is; they are split because the schemes are **not** a plain inversion, and the differences are the interesting part. Which layer carries the shape changes with the scheme: on light fabric the shading does it, but a dark shape over a bright desktop is a *hole* until something lights its edge, so on dark it is `rimLight` and `crownLight` that draw the edge at all, with the shading only filling in behind them. But there is very little room between the two failures: they are the *only* thing separating the canopy from the desktop, and pushed any further than they need to be they stop reading as a lit edge and start reading as a white line drawn round the shape — which is why dark ended up *below* light on both (0.46/0.15 against 0.90/0.34) despite needing them more. Light fabric is already brighter than most desktops and its silhouette reads on its own; those same numbers there would just blow the crown out to a flat white patch. `rimLight` also has to fall off fast in both: the stroke follows the whole silhouette, and a bright scallop hem reads as a second light source under the canopy that nothing else in the scene has. Shadows go deeper on light fabric than on dark, which has almost no room to go down before it stops being fabric at all. And the text colours are not the fabric's opposite but whatever survives sheer fabric over an unknown desktop, which is why `textShadow` is a dark shadow on one scheme and a white *glow* on the other. The apex stays **closed**: a vent there is what a real canopy has and it would remove the point where six seams converge and pile into a blot, but on a dome this squat it lands as a dark spot dead centre of the card, and it was tried and rejected. The seams fade out into the apex instead. The fabric is also **sheer**: its alphas run from 0.74 at the crown down to 0.56 at the hem, and `sheerness` is how much of the `.ultraThinMaterial` behind it shows. The two move together — thin fabric with nothing behind it is a tinted film over the desktop, and the material is what puts something *there*, a frosted layer the desktop arrives through softened. The alphas thin downwards for two reasons at once: the hem is the billowing edge and should be the lightest thing on the canopy, and the crown is where the card's text sits and so is the one part that has to keep enough body to hold white type. Even so, sheer fabric lets the desktop reach the type, which is why the text carries its own shadow — that, not a thicker canopy, is what keeps it legible over a bright desktop. Its colours are stated `ink`/`fadedInk` (white and a light grey) rather than `.primary`/`.secondary`, which would turn black on near-black the moment the desktop went light, and the alert/urgent accents are lifted well above the tones that suited white fabric. `crownLight` is the one reversal from the glass version, which deliberately had no highlight: a bright *spot* on glass is a light source that fails to move when anything else does, but `crownLight` is a broad diffuse falloff a third of the canopy wide — it is the shading, not a reflection, and the fabric flattens without it. Real refraction was never on the table and still isn't: on macOS 15 `.ultraThinMaterial` is a backdrop filter the compositor owns, so no `distortionEffect` shader or `CALayer` background filter can sample it; that would need macOS 26's `.glassEffect` or a captured-and-displaced backdrop (Screen Recording permission). `Domain/CanopyLighting` is the single light every layer takes its direction from — the gore tones, the lit side of each fold, where the crown sits, the bright side of the rim — so nudging it moves all of them together; a hand-picked tone per panel would fall out of agreement the first time anything changed. `Tests/ParaBearTests/CanopySnapshot.swift` renders the card to a PNG when `PARABEAR_SNAPSHOT` names a directory (`PARABEAR_SNAPSHOT=/tmp swift test --filter CanopySnapshot`); it is how the look gets judged by eye, since none of this is checkable by assertion. `ParachuteCanopy.sourceRect` shares its left edge and width with `RiggingLines.sourceRect` and stops at the hem, which is what makes the lines start exactly where the fabric ends — `RiggingLines.hemOverlap(forWidth:)` is the negative `VStack` spacing that lands them there. Lining the two up is necessary but not sufficient: the artwork's hem leaves every line straight up on both sides, so the two billows either side of it meet in a cusp of no width and the five inner lines hung from a point with nothing drawn at it, reading as loose below the canopy. `hemGather` splays the fabric sideways as it leaves each line so all seven have a visible tab to hang from; it is the shape's one departure from the artwork's coordinates, and `thereIsFabricAtEveryPointALineHangsFrom` is what keeps it.

Bear art ships as raw SVGs in `Assets/`, rendered via `SVGAssetView` (`Features/SVGAssetView.swift`), which loads them through `Bundle.packagedResources` and lets a view crop into a `visibleRect` of a larger `sourceViewBox` — this is how individual bear body parts (e.g. `bear_wave_arm.svg`) are composited/cropped from shared coordinate space rather than being separate pre-cropped files.

The bear's palette is the `<style>` block at the top of each of those files, and all three carry the same one: `cls-1` is the fur, `cls-2` the details it is read by — eye, claws, muzzle — and `cls-3` the belly contour (a 0.46-opacity stroke in the detail colour, which reads as a harness). The files on disk are authored in the **dark** scheme (near-black fur, white details) and `theArtworkOnDiskIsInTheDarkScheme` is what says so; the light scheme is those two colours swapped, applied on the way in rather than kept as a second set of files. Keep the three files in step — `bear.svg` and `bear_body.svg` share every path and `bear_wave_arm.svg` is a limb cropped out of the same coordinate space. The near-black is deliberately not `#000`: a pure black fill reads as a hole punched in the screen rather than as an animal, and it is the same blue-black the canopy mixes its shadows from.

`SVGAssetView.recoloured(_:_:)` does the swap, and it rewrites every `#rrggbb` in **one pass** for a reason worth keeping: the two schemes exchange two colours, and a substitution applied one rule after another cannot express an exchange — the first rule paints every black shape white and the second then paints all of them, the already-white ones included, black. `swappingTwoColoursKeepsThemDistinct` is the guard. Decoding and rasterising an SVG is far too slow to repeat per frame and the rig redraws at 60fps under a `TimelineView`, so results are cached keyed by file *and* recolouring — both schemes stay resident once seen and switching costs nothing.

### Greeting bubble

`Features/SpeechBubble.swift` traces the bubble from its artwork as **one** closed path — capsule plus tail — rather than assembling it from a `RoundedRectangle` and a separate little tail parked beside it at a hand-picked offset, which is what it was. The two were only ever nearly joined: the tail's base is a straight chord across the body's edge, so any half-point of drift left a seam, and it was visible because both are `.regularMaterial` and a material drawn twice over the same pixels is not the colour of one drawn once. One path has no seam to get wrong, and stating the artwork's own coordinates is what lets `SpeechBubbleTests` check the shape against the file it came from — the body is a true capsule, its radius exactly half its height, and a version with any smaller radius is not the drawn one. Scaling is uniform off the width for the same reason `ParachuteCanopy`'s is. `BearOverlayView` places it by `tailTip` and not by its corner: the corner is wherever the artwork's box happens to put it, but the tip is the thing that has to land on the bear's mouth. The text is centred in the **capsule** rather than in the canvas, which includes the tail — centring on the whole thing pushes the line down off the middle of the bubble by half the tail. `GreetingSnapshot` renders it under `PARABEAR_SNAPSHOT` like `CanopySnapshot`, because no assertion can say the tail points at the bear's face.

### App icon

`Packaging/AppIcon.icns` is generated by `Scripts/make_icon.swift`, not hand-drawn, so the paw is the *same* `pawprint.fill` the menu bar badges onto its calendar and the two read as one app. Three things it does deliberately. The body does not fill the canvas — macOS sizes every icon against the same 824-of-1024 grid, and a full-bleed square sits visibly larger than everything beside it in the Dock. The paw is the bear's own `#14161C` rather than `#000`, for the reason the artwork avoids pure black: it reads as a hole punched through rather than as a mark. And every size is drawn at its own scale instead of being resampled down from 1024, because the paw's toes are small enough at 16pt that resampling turns them to mush. The composition — paw held off the top-left corner — is the one thing that costs something: at 16pt the paw is roughly four pixels and the icon is close to a blank white square. It survives from 32pt up.

### Appearance

`Domain/RigAppearance.swift` is the rig's own colour scheme, and it is **not** the system appearance — the rig floats over an arbitrary desktop and is never behind a window's material, so the two are deliberately independent. It reaches the views by being passed down through initializers (`BearOverlayView` → `ParachuteEventCard` → `ParachuteCanopyView`, and → `BearCharacterView` → `SVGAssetView`), like every other dependency here. It is stored in `SettingsStore.appearance` and switched from the menu bar's "Appearance" row by `App/AppearanceToggleView.swift` — a capsule track with a knob that slides end to end, and one icon on whichever end the knob has left. That icon is the scheme you are *not* in (sun while dark, moon while light), so the control reads as "tap here to go there"; the knob would cover it otherwise, which is why a slider only ever needs one. The track previews what it selects, and nothing in it uses a semantic `NSColor` — a track painted in `.controlBackgroundColor` would flip with macOS while the thing it selects stayed put. It is AppKit rather than SwiftUI deliberately: it lives inside an `NSMenu`, which runs its own event-tracking loop, and a plain `NSView` is what reliably receives a click there. Its property is `scheme` rather than `appearance` because `NSView` already has an `appearance`, and it is exactly the `NSAppearance` this control exists not to be tied to. The knob's slide is an explicit `CABasicAnimation`: layers inside an `NSView`'s backing layer have implicit animations switched off. It subscribes to `settings.$appearance` rather than assuming it is the only writer.

### Menu bar icon

`App/MenuBarIcon.swift` composes the status item's icon, because SF Symbols has no `calendar.badge.pawprint`. Two things about it are worth keeping. The badge is not drawn *on top* of the calendar: a hole is punched clear through first — `.clear` compositing, alpha and all — and the paw sits inside it. That gap is the whole reason a badge reads as a badge; without it the paw's toes and the calendar's grid tangle into one smudge, which at 18 points is all anyone sees. And the calendar is drawn **smaller than the box**, shifted off the badged corner, which is what the system's own badged symbols do — a badged symbol is not the plain symbol with something stuck on it, and skipping the shrink leaves the badge eating the grid. The paw is fitted to the badge by `fit(_:in:)` rather than handed straight to `NSImage.draw(in:)`, which stretches: a pawprint is not square and came out squashed. The result stays a **template** image — the menu bar tints its own icons three ways (light bar, dark bar, and inverted again while the menu is open), and anything carrying its own colours opts out of all three. That last one is what `theIconIsATemplateSoTheMenuBarCanTintIt` guards.

### Settings

`SettingsStore` is the single source of truth for user prefs (bear visibility, alert/urgent thresholds in minutes, animation intensity, `WindStyle`, `PlannedFlightSpeed`), backed directly by `UserDefaults` with `didSet` persistence — no separate persistence layer.
